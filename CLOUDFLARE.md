# Cloudflare migration

*Started 2026-08-16. Replaces the Vercel plan in `README.md` §Deploying.*

Status: **foundation built and typechecking; route refactor and account provisioning still to do.**
Read §4 for exactly what is left.

---

## 1. Why this is not a normal Next.js deploy

`@duckdb/node-api` is a **native N-API addon**. Cloudflare Workers are V8 isolates
and cannot load native `.node` binaries — `nodejs_compat` does not change this.
`next.config.ts` already carries `serverExternalPackages: ["@duckdb/node-api"]`
for exactly this reason.

Every one of the site's 21 routes renders server-side through `src/lib/db.ts`
against 154 MB of local parquet. So the ordinary path — OpenNext → Workers —
fails on day one. This is an architecture change, not a config change.

**The resolution:** DuckDB never runs in production at all.

| When | Where DuckDB runs | What it does |
|---|---|---|
| Build (GitHub Action, Linux) | `@duckdb/node-api`, native | Prerenders every route against parquet |
| Runtime, interactive surfaces | `@duckdb/duckdb-wasm`, in the browser | Range-reads the same parquet from R2 |
| Runtime, everything else | nowhere | Static HTML off the edge |

The pipeline already rebuilds parquet nightly in CI, so the build-time half costs
nothing new. `BLUEPRINT.md` §6 anticipated the browser half.

## 2. The shape of it

```
GitHub Action (nightly 06:30 ET)
  python -m nflx.cli build          -> data/parquet   (154 MB, 81 files)
  npm run build                     -> web/out        (DuckDB native, build-time)
  node scripts/sync-r2.mjs          -> R2             (parquet + duckdb wasm)
  npx wrangler deploy               -> Worker + assets

Cloudflare
  Workers Assets   prerendered HTML/JS      served direct, no Worker invocation
  Worker           /api/espn/*              live game state
                   /data/*                  parquet + wasm, out of the R2 binding
                   /api/config              tells the browser where the store is
  R2               parquet + duckdb-*.wasm
  Browser          DuckDB-WASM              /lab, /stats, season switching
```

**Cost: $0/month, and no domain required.** Free tier covers 20,000 assets, 100k
Worker requests/day, and 10 GB R2. R2 charges no egress, which is what makes
serving 154 MB of parquet to browsers viable.

### Serving the data without a domain

`PARQUET_BASE` defaults to `/data` — a same-origin path the Worker serves out of
the R2 binding. That choice is what removes the domain requirement:

- R2's public `r2.dev` URL is rate-limited and explicitly not for production.
- An R2 custom domain is the right long-term answer but needs a domain.
- The binding needs neither, and being same-origin means **there is no CORS to
  configure at all** — removing a class of failure that only shows up in the
  browser, at runtime, with an unhelpful message.

The cost is Worker invocations: DuckDB-WASM issues a HEAD plus several ranged
GETs per query against a 100k/day budget. Comfortable to launch on.

**When a domain arrives**, add it as an R2 custom domain, apply
`scripts/r2-cors.json` with the real origin, and set `PARQUET_BASE` to it. The
browser then reads R2's CDN directly, `/data/*` stops being hit, and Worker
invocations fall back to just the live ESPN calls. No code change.

### Two limits that dictate the design

- **Workers Assets caps a single file at 25 MiB.** `duckdb-mvp.wasm` is 41 MB and
  `duckdb-eh.wasm` is 36 MB. They **cannot** ship as static assets — they go to R2.
  The worker *scripts* are under 1 MB and stay in `public/`, which also sidesteps
  the browser's refusal to run `new Worker()` against a cross-origin URL.
  `scripts/stage-duckdb.mjs` enforces the split and fails the build if a future
  release pushes a worker script over the limit.
- **20,000 assets on the free tier.** See §4.1 for why this rules out prerendering
  every season of every route.

## 3. What is already built

All of this typechecks (`tsc` clean for both app and Worker) and the sync script
is verified against the real data store. None of it changes how the site runs
today — the Cloudflare layer is additive until `output: "export"` is switched on.

| File | What it does |
|---|---|
| `web/wrangler.jsonc` | Assets, R2 binding, vars, preview environment. `run_worker_first` limited to `/api/*` so prerendered pages never wake the Worker |
| `web/worker/index.ts` | ESPN proxy on a closed endpoint whitelist, 20 s edge cache, `/api/config`, asset fallthrough |
| `web/worker/tsconfig.json` | Worker compiles against workerd globals, outside Next's `**/*.ts` glob |
| `web/worker/worker-configuration.d.ts` | Generated by `npm run cf:typegen`. Rerun after any binding change |
| `web/src/lib/db-client.ts` | Browser query layer. Mirrors `db.ts`'s `query`/`queryOne`/`table`/`pbpGlob` so queries port over unchanged |
| `web/scripts/stage-duckdb.mjs` | Splits the WASM runtime across `public/` and R2, with the 25 MiB guard. Runs on `prebuild` |
| `web/scripts/sync-r2.mjs` | Incremental R2 sync keyed on an md5 manifest. Verified: 83 files, 231 MB |
| `web/scripts/r2-cors.json` | CORS allowing `Range` and exposing `content-range`/`accept-ranges` — required for DuckDB-WASM |
| `.github/workflows/pipeline.yml` | `deploy` job: build → sync R2 → deploy. Data ships before the pages that read it |

### Why the ESPN call is proxied rather than made from the browser

1. ESPN sends no CORS headers, so a direct fetch from the page is blocked.
2. Their edge fingerprints clients and 403s some of them, and browsers will not
   let script set request headers like User-Agent. This caused a silent, total
   outage of every live surface once already — `HANDOFF.md` §5.

**Correction to `HANDOFF.md` §5, measured 2026-08-16.** That entry attributes the
403 to a User-Agent carrying a `name/version` token. The real rule is lower down
the stack. Identical requests to `/scoreboard` from this machine:

| Client | Result |
|---|---|
| Node `fetch`, every User-Agent tried (incl. `name/version`) | 200 |
| curl, its own default UA | 200 |
| curl, every other UA — custom, browser-like, or absent | 403 |

So the discriminator is TLS fingerprint or header ordering, not the UA string.
The practical consequences: the app is fine (it runs on Node), **curl is useless
for testing this endpoint**, and workerd is a third client whose behaviour
neither result predicts. **Verify the live path against the deployed Worker**;
if live surfaces go quiet after deploy, this is the first thing to check.

The proxy uses a closed whitelist (`scoreboard`, `summary`, `standings`, `teams`,
`news`) and forwards only known query params. An open proxy would let anyone run
traffic through the account's quota.

## 4. What is left

### 4.1 The route refactor — the bulk of the work

**The problem:** 16 of 21 routes read `searchParams` server-side (season pickers,
position/week/category/view filters). Under `output: "export"` searchParams are
**always empty at build time**, so a naive export would silently break season
navigation across the whole site. Silently is the operative word — pages would
render, just always showing the default season.

| Route | Params |
|---|---|
| `/draft`, `/playoffs`, `/separation`, `/standings`, `/teams`, `/tools/fourth-down` | `season` |
| `/teams/[team]`, `/players/[id]` | `season` |
| `/scores` | `season`, `week` |
| `/fantasy` | `season`, `pos` |
| `/fantasy/week` | `week`, `pos`, `view` |
| `/war` | `season`, `pos`, `view` |
| `/leaders` | `cat` |
| `/tools/armchair-gm` | `team` |
| `/lab`, `/stats` | arbitrary `Record<string, string>` |

**The decision: prerender the current season only, switch client-side for the rest.**

Prerendering every combination is ~5,900 pages → ~12,000 files with RSC payloads.
That fits under 20,000 but leaves no headroom. Prerendering the current season for
every route gives ~2,900 pages (~6,000 files) and covers essentially all traffic
with real HTML — which is what SEO and first paint need. Historical seasons are
the long tail; they re-query through `db-client.ts` in the browser.

Per route, the pattern is:

1. Keep the server component. It renders the **default** (current) season at build.
2. Add a client component that reads `useSearchParams()`; when the param differs
   from the prerendered default, it re-queries via `db-client.ts` and swaps the
   table in.
3. Because `db-client.ts` mirrors `db.ts`'s API, the SQL in `queries.ts` is
   reusable — extract the shared query strings rather than writing them twice.

**Do not let the two layers drift.** `normalize()` is duplicated in `db.ts` and
`db-client.ts` and must stay byte-for-byte identical; if it drifts, the same query
returns different values depending on whether it ran at build time or in the
browser. That is precisely the class of silent data bug this project has been
bitten by twice (`HANDOFF.md` §5).

### 4.2 Route-specific work

- **`/lab` and `/stats`** — fully client-side. Their param space is unbounded, so
  there is no prerendering to do beyond the shell. This is also the surface
  DuckDB-WASM was chosen for; call `preload()` on mount so the ~10 MB runtime
  downloads while the reader is still reading.
- **`/games/[id]`** — currently `force-dynamic` for live ESPN state. Becomes a
  prerendered shell plus a client component hitting `/api/espn/summary?event=`.
  `src/lib/espn.ts` is `import "server-only"` and needs a client twin; keep the
  parsing functions and swap only the fetch.
- **`/players/[id]`** — 11,352 players have a season row, but only 2,827 appear in
  the last three seasons. `generateStaticParams` should return that recent set;
  the 8,525-player historical tail renders client-side. Prerendering all 11k is
  possible under the asset cap but the build time is not worth it.
- **`pbpGlob()`** — `db-client.ts` throws when called without a season. HTTP has no
  directory listing, so DuckDB-WASM cannot glob `pbp/*.parquet`. Any query relying
  on the glob must name its seasons explicitly.

### 4.2b The four API routes

`output: "export"` emits no server, so every Next route handler stops existing.
All four need a home:

| Route | Used by | Where it goes |
|---|---|---|
| `src/app/api/live/[id]` | `LiveGame.tsx` polling | The Worker's `/api/espn/summary?event=` — already built |
| `src/app/api/search` | `PlayerSearch.tsx` | Prebuilt static player index + client-side filter (Fuse.js), as `BLUEPRINT.md` §6 planned |
| `src/app/api/stats/export` | `/stats` CSV export | Client-side: DuckDB-WASM `COPY … TO`, or serialise the already-loaded rows |
| `src/app/api/fourth-down` | `FourthDownCalculator.tsx` | Client-side against `fourth_down_grid.parquet` in R2 |

The fourth-down grid is 4.6 MB and precomputed, so a ranged read of the relevant
partition is cheap — this is a good first exercise of the WASM path.

### 4.3 Account provisioning — needs an interactive login

`wrangler login` is an OAuth flow and could not run in the session that built this.
Nothing below has been executed against a real account. Run in `web/`:

```bash
npx wrangler login

# One bucket is enough to start. The preview one keeps experiments off
# production data and can wait.
npx wrangler r2 bucket create gridiron-parquet

# First data push (~231 MB; subsequent syncs only move what changed).
npm run cf:sync
```

That is the whole prerequisite. **No bucket CORS, no public bucket access and no
domain** — the Worker serves the store same-origin from the binding, so none of
those apply. `npm run cf:cors` and `wrangler r2 bucket domain add` are only for
the later custom-domain setup described in §2.

The site lands on `gridiron-analytics.<account>.workers.dev`, which is free,
HTTPS, and permanent. A custom domain can be pointed at it any time afterwards
without redeploying.

Then set, in the repo's Actions settings:

| Kind | Name | Value |
|---|---|---|
| Secret | `CLOUDFLARE_API_TOKEN` | Token with *Workers Scripts: Edit* and *Workers R2 Storage: Edit* |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | From the Cloudflare dashboard |
| Variable | `PARQUET_BASE` | Leave unset while using `/data`; set it only when a custom domain exists |

**The origins in `scripts/r2-cors.json` are placeholders** and only matter under
the custom-domain setup. If you switch to it, change the CORS origin list and
`PARQUET_BASE` together — a mismatch fails only in the browser, at runtime, with
a message that does not obviously point at CORS.

### 4.4 Order to do it in

1. Provision (`wrangler login`, bucket, `cf:sync`). Proves credentials and gets
   the data layer live. Independent of everything else.
2. Convert `/lab` and `/stats` to client-side, and the fourth-down calculator off
   its API route. Least SEO-sensitive, and they exercise the whole WASM path.
3. Convert `/games/[id]` and `/api/live` onto the Worker's ESPN proxy.
4. Then the 16 searchParams routes, in traffic order, plus `/api/search` and
   `/api/stats/export`.
5. Switch `output: "export"` on last, once nothing depends on request-time
   rendering, and deploy. Turning it on earlier just produces confusing build
   failures — `out/` does not exist until then, so `wrangler deploy` cannot run
   before this point either.

## 5. Local development

Unchanged: `npm run dev` still runs the normal Next server with native DuckDB
reading `../data`. Nothing about the Cloudflare layer affects the dev loop.

To exercise the Worker and the assets pipeline together:

```bash
npm run build        # prerender (needs a built ../data)
npm run cf:dev       # wrangler dev: Worker + out/ on :8787
```

`db-client.ts` falls back to a relative base when `/api/config` is unavailable, so
under plain `next dev` it reads parquet from `public/` rather than R2.

## 6. Things that will bite

- **The 25 MiB asset limit** is per file and is not negotiable. If a build ever
  emits a large file into `out/`, the deploy fails late. `stage-duckdb.mjs` guards
  the known case; nothing guards a future one.
- **`wrangler types` must be rerun** after any change to `wrangler.jsonc`, or the
  Worker typechecks against stale bindings.
- **The R2 manifest is written last** by `sync-r2.mjs` on purpose. An interrupted
  sync re-uploads rather than claiming files landed that did not. Do not "optimise"
  this by writing it first.
- **`r2.dev` is not for production.** It is rate-limited. Use a custom domain.
- **Free tier Worker invocations** are 100k/day. `run_worker_first` is scoped to
  `/api/*` precisely so prerendered pages never touch the Worker. Widening that
  pattern is the fastest way to blow the quota.
- **Do not add `nodejs_compat` and try to import `@duckdb/node-api` in the Worker.**
  It will not work, for the reason in §1, and the failure mode is a confusing
  bundler error rather than a clear one.
